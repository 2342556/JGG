# JGG — Architecture decisions (ADRs)

## ADR-001 Zero-install toolchain (build environment had no npm registry access)
**Context:** `npm install` returned HTTP 403 for every package. Available offline: Node 22.22 (native TypeScript type-stripping, `node:sqlite`, `node:test`), esbuild 0.27.7 (bundled with a global tsx), React 19.2.5, Python Playwright + Chromium.
**Decision:** API/worker run as plain `node *.ts` (erasable TypeScript only: no enums/namespaces/parameter properties; `.ts` import suffixes). HTTP uses a thin `node:http` router (Fastify-shaped, swappable). Runtime validation uses an in-repo schema module (`packages/contracts`) instead of zod. Web is React bundled by esbuild. The candlestick chart is an in-repo canvas renderer (Lightweight Charts unavailable). Tests: `node --test`; e2e: Python Playwright.
**Consequences:** no lockfile could be generated; `package.json` pins the versions used. Strict `tsc` type-check runs against small offline shims (`types/node-shim.d.ts`, `apps/web/react-shim.d.ts`) because `@types/node`/`@types/react` are not installable; replace the shims when online. In a networked environment: `npm install`, add `tsc --noEmit`, optionally swap in Fastify/zod/Lightweight Charts behind the same interfaces.

## ADR-002 SQLite (WAL) for dev/test, PostgreSQL + RLS for production
**Decision:** The app code is owner-scoped on every query (tested, T14). The production schema (`infra/postgres/migrations`) adds `FORCE ROW LEVEL SECURITY` owner policies, NUMERIC money columns, CHECK constraints (e.g. `reserved <= qty`) and a deferred double-entry trigger. The app role `jgg_app` has no BYPASSRLS; each request does `SET LOCAL jgg.user_id`.
**Evidence:** applied to the dedicated Supabase project "JGG AI TRADING" (`mmpjzxvqvhqeucasswqz`, PG 17.6) in schema `jgg`; RLS/journal/check verification ran as `jgg_app` and rolled back; security advisors: 0 findings. Rollback: `DROP SCHEMA jgg CASCADE; DROP ROLE jgg_app;`.
**Open:** the Node app does not yet have a Postgres repository implementation (no `pg` driver offline). Port the `db.ts` helpers to `pg` with per-request transactions when network is available.

## ADR-003 Modes and execution authority
Demo and Paper both use the paper simulator (`jgg-paper-cpmm-v1`, disclosed on /status) and tag every record with its mode. `live_readonly` refuses trading (POLICY_DENIED) and refuses to show fixtures as live data (PROVIDER_UNAVAILABLE). `live` cannot be selected (CAPABILITY_BLOCKED) until a verified execution provider, signer and owner-authorized funded test exist. Mode changes invalidate pending approvals and release reservations.

## ADR-004 Execution safety
Order + attempt are persisted before dispatch; a dispatch claim (`order_attempts.outcome` from NULL → `dispatching`) guarantees one dispatch per order even on replayed/concurrent requests (bug found in testing and fixed). Terminal validation outcomes (expired quote, mode change, kill switch) are committed before the error is returned — throwing inside the transaction had rolled them back (bug found and fixed). Timeouts become `reconciliation_required`; the worker reconciles against external truth and never resubmits.

## ADR-005 Automation is deny-by-default
Risk policy defaults to DENY_ALL. Strategies are created as drafts and activated only by the owner in an interactive session with a configured policy and allowed chain. Every automated submission passes `checkRisk` with the policy version captured at grant time; the kill switch bumps the version and pauses strategies.

## ADR-006 AI
No LLM key: a deterministic keyword planner (`jgg-rule-planner-v1`) is used and labeled. AI never holds `trade:execute`/`launch:execute`; trade tools create intents awaiting user approval. Third-party text (token names, metadata) is rendered as inert text.

## ADR-007 Demo clock and fixture universe
Fixture market data is deterministic from a fixed epoch (2026-09-25T00:00Z). The API and worker share a demo clock anchored in `worker_state`. New tokens "launch" every 150 s of demo time so the New column stays alive. Clients count quote TTL relative to receipt (`ttlMs`) because the demo clock is not wall time (bug found in e2e and fixed).

## ADR-008 Branding
Original JGG wordmark + pixel monogram, generated geometric token avatars, own SVG icons. No GMGN frog/logo/assets. No income promises on Rewards; JGG fee is 0 bps so commissions are 0.

## ADR-009 Offline behaviour (PWA)
The service worker caches only the app shell. `/api/*` is never cached, and nothing (quotes, approvals, orders) is queued for later replay; offline users see the shell, an offline banner and error states.

## ADR-010 Automation waits on unresolved submissions
If any order of a user is `reconciliation_required` (crash, timeout, restored database), that user's strategies are not evaluated until reconciliation settles it; this avoids acting on balances that may be wrong.

## ADR-011 GMGN as the market-data provider, integrated through the official gmgn-cli
Owner selected GMGN (2026-09-25). GMGN documents its OpenAPI through the MIT-licensed `gmgn-cli` + agent skills (github.com/GMGNAI/gmgn-skills). JGG calls only documented CLI commands/flags (`market trending|trenches|kline`, `token info|security|…`, `track smartmoney`) via `packages/providers/src/gmgn.ts`, never private web endpoints. Read-only: the request-signing private key is not passed to the CLI. Rate limit: documented leaky bucket (rate 10, capacity 10) → JGG spaces calls ≥125 ms and honours `X-RateLimit-Reset` bans. GMGN requires IPv4 egress and, for swaps, an IP whitelist + signing key; unattended CLI trades additionally require `GMGN_ALLOW_AUTOMATED_TRADES=1 --yes`.
**Status:** SUPPORTED by docs, not VERIFIED — the field mapping (`mapRankItem`) is tolerant and keeps unknowns null until `scripts/verify-gmgn.mjs` captures live samples. Swap/condition-order argument builders exist and are unit-tested but `runGmgn` refuses execution commands (T59).
**Trailing:** GMGN condition orders document only `profit_stop`/`loss_stop` fields; trailing parameters are not documented, so trailing stays in the JGG worker.

## ADR-012 Auto trader and the win-rate question
Owner asked for an automatic finder + auto trading with a 70–90% win rate and exits "partial/trailing at +50%, TP at +100%". Implemented: `jgg-finder-v1` (hard safety gates, unknown never passes, explainable score = ranking not probability), `auto_trader` strategy (one new pick per scan, no re-buys, max positions, risk policy, kill switch), and the exit plan (sell 50% at +50% and arm a 15% trailing stop on the rest, take the rest at +100%, −30% hard stop; all configurable). **No win rate is promised or displayed as a target.** The UI shows the measured win rate with the count of closed trades and states when the sample is too small. Results on fixture data say nothing about real markets; the next step is paper trading on live GMGN data to measure it honestly.

## ADR-013 Standalone live data (Option B, owner decision 2026-09-25): own indexer, no GMGN dependency
**Decision:** JGG builds its own Solana pump.fun data pipeline (`packages/providers/src/solana/*`, `apps/api/src/live.ts`, `apps/workers/src/indexer.ts`). Only commodity infrastructure is external: a standard Solana RPC (replaceable) and Jupiter Price API v3 for SOL/USD. The GMGN adapter stays in the repo but is unused.
**Verified (docs + official vectors):** pump program id, Global defaults, bonding-curve PDA/fields and `complete` rule, market-cap formula, tiered fees (pump-public-docs); Anchor event discriminator derivation checked against the official Anchor docs sample; `EVENT_IX_TAG_LE` bytes; TradeEvent 21-field order from two independent decoders; Jupiter Price v3 URL/header/omission semantics; standard RPC method shapes.
**Design rules:** decode a documented field prefix and ignore appended fields (pump appends fields over time); attribute `Program data:` lines to the executing program via the invoke/success stack; decode `emit_cpi` events only when program id AND tag match; never index failed transactions; never let an older slot overwrite newer curve state; fees from the latest observed TradeEvent (protocol + creator bps), fallback 125 bps flagged as estimated; quotes refuse stale reserves (>15 min), missing SOL/USD, graduated curves.
**Honesty rules:** the Finder only scores coins seen from creation (complete history); honeypot = 'safe' only after an RPC security check shows no freeze authority and no risky Token-2022 extensions while the coin is on the curve (program-guaranteed sells); KOL factor is excluded (no social data) and the rubric version says so; smart-money labels are derived from our own 7-day history (`jgg-smart-v1`) and are empty during warm-up. Fixture-driven features (copy trading, snipes, wallet rank, signals, most skills) are disabled in live mode instead of mixing simulated data with live data.
**Self-check in production:** every indexed buy re-derives its token amount from x*y=k; the mismatch rate is published on /status (`modelMismatchRate`).
**Not verified here:** a real mainnet stream (no network in the build environment). `scripts/verify-live.mjs` produces the evidence on the owner's machine.

## ADR-014 Optional FOMO labels (fomoapi.io)
fomo.family has no official API. `fomoapi.io` is an independent, unofficial service (documented base URL, bearer key, credits). JGG uses only its leaderboard's wallet→handle labels (hourly, credit-reserve guard) and joins them with trades from its OWN index, so every "FOMO trader bought X" signal is backed by on-chain trades JGG saw itself. FOMO-reported PnL is shown as such. Trading never depends on it. Its hosted "trading accounts" are not used (third-party custody).

## ADR-015 Custodial trading wallet (owner decision) and live execution
Off by default; requires server config + a wallet-verified, allow-listed account (demo accounts can never hold funds). Keys: server-generated ed25519, AES-256-GCM with a master key from env, AAD bound to user+address, decrypted only inside the signing call. Execution: Jupiter Swap v2 `/order` (taker = trading wallet) → route must meet the approved `minOut` → RPC simulation must not spend more SOL (input + 0.015 SOL buffer) or tokens than approved → sign → persist signed bytes → `/execute` → fill read from the chain (`getTransaction` balances). Timeouts → reconciliation: re-send the identical signed transaction inside Jupiter's ~2-minute idempotency window, else expire once the signature is unseen; unknown signatures → manual-check notification. Per-trade/daily caps, per-user spend lock, kill switch. Withdrawals: SOL only, to the verified sign-in wallet only, simulated before sending.
**Known limits:** no token withdrawals (sell first); graduated-coin automated exits use a price floor from the last curve price (fails safe if the market is lower — sell manually); single-server SQLite; the master key on the same server is a risk accepted for single-owner use — do not offer this to other people without legal review (custody of customer funds is regulated).

## ADR-016 Finder outcome tracking (owner: "paano natin masisiguro na malaki ang winrate") — evidence, not scope
Instead of adding more terminal features, this pass built the evidence engine the accuracy claim needs. Every coin that PASSES the Finder is tracked forward from that moment — regardless of whether any user actually bought it — using only reserves this indexer already has (no extra RPC calls). This is deliberately independent of any one auto-trader run: it gives a far larger, faster sample than waiting for real trades, and it is the thing to look at before enabling live trading.
**Method:** `jgg-finder-v1` pass → snapshot entry curve reserves → sample price change at 5/15/30/60/120/240/720/1440 minutes since scan (whenever the worker tick next runs past that mark) → close the row as `rugged` (price ≤ -80% AND liquidity ≤ 1/5 of entry, checked only after 5 min to avoid noise), `graduated` (left the curve — v1 does not follow price after migration), or `timeout_24h` (still on-curve, neither). Stats report sample size, median/average move and ≥+50%/≥+100% hit rates **per horizon**, with an explicit small-sample caveat below ~30 and a reminder that a hit rate is not a trading return (no fees/slippage/fill risk included).
**Evidence:** `tests/api/finderOutcomes.test.ts` — a synthetic pump correctly produces the expected bps at the 5-minute mark; a synthetic dump (curve price down >97%, real SOL reserves drained to 0) is classified `rugged` and stops sampling; a `CompleteEvent` freezes tracking as `graduated`; a quiet coin times out at 24h; stats aggregate correctly and warn on small samples.
**Not yet true:** there is no real sample — this only becomes meaningful after the indexer runs continuously against mainnet for days to weeks. The panel shows exactly that (`—` everywhere) until then; it never fabricates a rate to fill the table.
